# Design decisions

## D001 — Milestone boundaries and approved specification interpretations
Milestones are in Section 16; Section 0 now points there. M1 ends after foundation and facts ingestion, and acceptance remains pending until the student verifies the revenue fixture and confirms the milestone. Quant tools are required for production LLM arithmetic, while deterministic ingestion/evaluation calculations and the explicit no-quant ablation are allowed; diff is optional in M4, and improvements are selected on dev before final test reporting.

## D002 — Isolated Python and dependencies
Use uv 0.13.1 with project-local Python 3.12.15, `.venv`, and `uv.lock`; system Python 3.14 is unchanged. Only M1 dependencies are installed, including explicitly approved `pydantic-settings`, with YAML support deferred. Explicit virtual-environment executable paths avoid changing PowerShell execution policy.

## D003 — Window and cutoff
The initial snapshot ID is `2026-10-19-v1`, with an inclusive filing-date cutoff of **2026-10-19**, interpreted in the user's America/New_York calendar. Ingest three completed fiscal years for which annual reports are available, plus available subsequent quarters; a fiscal year whose annual report has not yet been filed cannot supply a complete annual dataset. Historical submissions are traversed over a conservatively broader window so recent-list truncation does not omit required filings or prior annual boundaries.

## D004 — Immutable versioned snapshots
Store successful response bodies under `data/raw/<snapshot_id>/<sha256(url)>.body`, with URL, retrieval timestamp, content type, and body hash in companion metadata. Completed cache entries are never refreshed, corruption fails explicitly, and changing the cutoff requires a new snapshot ID. A snapshot captures responses acquired during its construction, filtered by filing date, rather than reconstructing the SEC's exact historical state; the database records a manifest of acquired responses.

## D005 — SEC fairness and retry behavior
Use one shared client per ingestion, spaced at least 1/8 second between network attempts, including retries; cache hits make no network request. Retry 429, 5xx, and transport failures with bounded exponential backoff and jitter, honoring Retry-After up to a 120-second bound, while other HTTP failures remain explicit. A descriptive User-Agent is required; error pages and invalid JSON are never cached as successful data, and only one ingestion process should run against this project at a time.

## D006 — Reporting-date fiscal calendars
Anchor each completed fiscal year to actual 10-K report dates and its observed annual duration start, with the previous annual end plus one day as fallback. Actual 10-Q report dates define quarter boundaries, handling 52/53-week years without approximating quarters from months; `fiscalYearEnd` is retained as supporting metadata. Observed boundaries take precedence over Section 7.1's approximate day bands: Costco's 12/12/12/16-week calendar has a 16-week Q4 and shorter YTD durations that those bands would incorrectly reject. Completed fiscal years are labeled by their ending calendar year, a partially reported subsequent year is provisionally labeled the next fiscal year, and ambiguous or incomplete boundary sets fail instead of guessing.

## D007 — Concept selection and missing metrics
Choose one direct fact per metric/period using the specified concept priority, falling back to later concepts only when earlier concepts lack that period; direct reported quarters take precedence over derived alternatives. Retain the actual concept on every fact and never sum overlapping concepts. Missing standard-taxonomy facts are marked unavailable with a reason; `not_applicable` is a distinct supported status that requires positive evidence and is never inferred solely from absence.

## D008 — Revisions and exact values
For each concept, unit, start, and end context, choose the latest filed observation within the cutoff, with accession as a deterministic tie-breaker; conflicting values in the same filing/context fail explicitly. Decode financial values into Decimal and store NUMERIC, preserving raw USD and USD/shares units rather than converting to display millions. This is latest-filed-within-snapshot data, not an as-originally-reported historical time series.

## D009 — YTD derivations and provenance
For additive duration metrics, derive missing Q2 as 6M minus Q1, Q3 as 9M minus 6M, and Q4 as FY minus 9M, with FY minus three direct quarters as Q4 fallback. Inputs must share the exact fiscal-year start, compatible adjacent boundaries, concept, and unit; EPS is never derived, and gross profit is never synthesized from revenue and costs. Every derived fact retains signed input values, concepts, dates, units, filing dates, and accessions in `derivation_inputs`, including YTD observations that are not standalone stored facts.

## D010 — M1 schema finalization
Extend the supplied schema with `ingestion_snapshots`, snapshot-aware facts, `source_filed`, derivation-input JSONB, and `metric_availability`; retain the later-stage tables and indexes specified in Section 6 without implementing those stages. The fact uniqueness key includes snapshot, company, metric, period type, start date, end date, and unit, using PostgreSQL 16 `NULLS NOT DISTINCT` so instant facts also deduplicate. Schema changes after M1 require approval; migrations have checksums and run transactionally under an advisory lock.

## D011 — Stable fact IDs and resumption
Upserts preserve company/filing identity and fact conflicts do not replace existing canonical rows within an immutable snapshot. Each company is one database transaction, so failures roll back that company while prior companies and cached downloads remain reusable. Snapshot-specific facts coexist across refreshes, while company and filing metadata are shared; raw snapshot manifests preserve their original sources.

## D012 — Instant facts at fiscal year end
Store year-end balance-sheet instants once under Q4, rather than duplicating one observation as both Q4 and FY. The future metric interface must resolve FY to the same year-end instant; no summation of balance-sheet values is valid. This avoids fighting the approved uniqueness key, which identifies an instant by its company, metric, end date, unit, and snapshot.

## D013 — Windows database compatibility
The CLI selects Windows' selector event loop because Psycopg asynchronous connections do not support the default Proactor loop. For a configured `localhost` database, supply IPv4 `hostaddr=127.0.0.1` to avoid the observed IPv6 connection delay while preserving the configured hostname and credentials. Pools open, wait for readiness, and close explicitly with bounded connection timeouts.

## D016 — Documentation checks and deferred integrations
Reviewed official [SEC APIs](https://www.sec.gov/search-filings/edgar-application-programming-interfaces), [SEC access policy](https://www.sec.gov/about/webmaster-frequently-asked-questions), [Psycopg pools](https://www.psycopg.org/psycopg3/docs/advanced/pool.html), [Psycopg async compatibility](https://www.psycopg.org/psycopg3/docs/advanced/async.html), [Pydantic migration](https://github.com/pydantic/pydantic/blob/main/docs/migration.md), [HTTPX timeouts](https://www.python-httpx.org/advanced/timeouts/), and [uv Python provisioning](https://docs.astral.sh/uv/guides/install-python/). ## D017 — Approved model-token chunking deviation
The student explicitly replaced SPEC.md §7.3's approximate tiktoken 600/800/80 settings with the embedding model's own tokenizer: target 380 tokens, maximum 460 including contextual header and special tokens, and approximately 50 tokens of overlap. Ordinary chunks receive exactly one embedding; they are never window-averaged. Because the reranker uses a different tokenizer, construction also reserves 48 reranker query tokens plus pair special tokens within 512; query-time checks reject longer queries or overflowing pairs instead of silently truncating them. These constraints take priority over the approximate target, and table boundaries can reduce overlap.

## D018 — Oversized table rows and source coverage
Stored table rows remain indivisible, with headers repeated when a table continues in another chunk. A single row that cannot fit either model's budget is explicitly flagged; only these flagged citation units use overlapping model-input windows, with mean-then-normalized embedding vectors and maximum reranker-window score. Ordinary prose is split at whitespace using the actual tokenizers, retaining source text and block ranges; preserving source coverage takes priority over exact overlap size.

## D019 — Deterministic passage identities and versioned corpora
The approved M2 migration replaces unused serial passage identities with full SHA-256 text IDs, leaving M1 financial tables and migration checksums intact. Section IDs hash accession, raw-body hash, processing fingerprint, item and occurrence; chunk IDs hash section identity, ordinal and canonical text, so insertion order and database rebuilds do not affect citations. Processing fingerprints include parser/chunker versions, model-tokenizer revisions, budgets and relevant package versions; changed processing creates a separate corpus rather than rewriting labeled passages. Corpus membership, document provenance and processing checkpoints are stored separately, and labeling freezes a complete corpus.

## D020 — DOM section boundaries and repeated running headers
Collect all Item headings to determine section ends, then retain only the items required in §7.2; choose the largest substantive span among duplicate candidates to avoid table-of-contents entries. Repeated 10-Q Part labels do not introduce new boundaries unless the part actually changes, and multi-item page headers such as Microsoft's "Item 3, 4" are ignored. Missing items are recorded as diagnostics, while unresolved tiny spans and filings without retained sections fail explicitly; no missing content is fabricated. The three real regression fixtures are Apple accession 0000320193-25-000079, Microsoft 0000950170-25-061046, and NVIDIA 0001045810-25-000023.

## D021 — Filtered vector search guarantees
Use exact cosine ranking over a materialized eligible relation for company/year/period searches, avoiding post-index filter starvation on small subsets. Broader searches use transaction-local HNSW strict iterative scans with ef_search 100, followed by an exact rerun whenever the internal candidate pool underfills; this guarantees min(requested depth, eligible embedded rows), rather than assuming iterative scans always finish. The real pgvector regression test verifies an HNSW plan under a restrictive scan cap, triggers fallback, and compares recovered IDs with an independent exact oracle. Keyword search may legitimately return fewer hits when fewer documents match.

## D022 — Retrieval ranks and human-only evaluation
All modes return at most public k, using an internal candidate depth of max(30,k); hybrid fusion uses the spec's reciprocal-rank constant 60 and chunk ID tie-breaking. Evaluation reports macro recall@5/10 and explicitly truncated MRR@30, without inventing a quality threshold absent from the spec. The labeling CLI pools all four modes, deduplicates candidate IDs, supports browsing beyond the pool, and accepts only student-written questions, relevance judgments and optional reference answers. Human labels reference an explicitly frozen corpus; pooled judgments are not claimed to be exhaustive relevance annotations.

## D023 — Resumption, local models and approval gates
Downloads retain the existing immutable URL cache and identifying SEC client; parsing commits each filing with its checkpoint, while embedding commits bounded batches and resumes only missing or incompatible vectors. Model revisions are pinned before downloading and artifacts live under ignored data/models; the approved direct dependencies are selectolax and sentence-transformers, with tokenizer/model runtimes coming from its locked dependency tree and no tiktoken dependency needed. M2 rechecked official SEC, pgvector and BGE documentation; selectolax 1.0 uses the maintained Lexbor backend because its old parser backend now raises an import error. The full embedding run requires the student's go-ahead after a measured CPU sample; no handwritten retrieval evaluation or M3 work starts before the separate student handoffs.

## D024 — SEC tables without semantic header cells
Real corpus tables commonly use td cells throughout rather than th, so explicit th headers take precedence and a short leading row of a multi-row, multi-column table is the fallback header. Limit inferred headers to 400 characters and exclude Item/Part navigation rows to avoid copying long layout prose or contents headings into continued chunks. Original row text remains unchanged; this is a conservative formatting heuristic rather than a claim to recover every multi-level table header perfectly.

## D025 — Scope-independent identities and database connection state
Hash only processing configuration into section/chunk fingerprints; selected tickers and filing count belong to corpus identity, so expanding the ingestion scope cannot change a pre-existing passage ID. A real-filing regression test rebuilds empty passage tables and expands from one to two filings while checking the original IDs. All ingestion stages share a schema-scoped advisory lock, allowing isolated test schemas without simultaneous production ingestion. Reset pooled connections' client-side row factories because dictionary row settings otherwise survive checkout and can break later tuple-based reads.

## D026 — Retrieval caching after corpus freeze
Persist ranked hits under ignored data/retrieval_cache only for a frozen corpus, keyed by corpus ID, question, filters, mode, depth, embedding fingerprint, reranker revision and retrieval implementation version. Partial embedding runs never populate that cache, preventing incomplete candidate pools from being reused once the corpus is ready; interrupted labeling/evaluation can reuse already scored queries without changing any human gold labels.

## D027 — Primary retrieval metric amendment to D022
Before evaluation results were seen, the student chose capped recall@k, |gold ∩ top-k| / min(k, |gold|), as the primary metric for k=5 and 10. This removes the unavoidable 5/6 and 5/7 ceilings at k=5 for the two deliberately broad questions; standard recall, hit rate, and MRR@30 remain reported alongside it, macro-averaged across questions. Every mode retrieves to depth 30 and the reranker scores the full hybrid top 30, with saved filters unchanged; report the full 30, six intentionally cross-year searches and 24 period-filtered searches separately. Paired comparisons count per-question wins/ties/losses on primary capped recall@10, chosen before computing results; n=30 is descriptive, not conclusive evidence of small differences.

## D051 — M4 SDK versions and the 2026-10-21 API version (approved)
Use the current official SDKs listed in SPEC §3: `anthropic==2.1.0`, whose 2.0.0 release adopted API version 2026-10-21, and `openai` 3.36.x for OpenAI-compatible Chat Completions, with exact versions locked in uv.lock; `mcp==2.3.0` is unchanged. The alternative, `anthropic` 1.17 on API version 2023-06-01, would keep `temperature` but delay an unavoidable migration, and current Claude models already accept only default sampling. As approved, `anthropic` is pinned exactly to 2.1.0 and `openai` to 3.36.x; if 2.1.0 misbehaves in Phase C, the failure is reported before any version change.

## D052 — Hand-written agent loop instead of the SDK tool runner (approved)
The Anthropic SDK now provides a beta tool runner, but SPEC §0.2 and §10.3 require a hand-written loop and the runtime must also drive OpenAI-compatible endpoints. A manual loop gives one provider-neutral place for budgets, argument locks, untrusted-data envelopes, tracing and replay. Assistant turns are replayed from the provider's exact content blocks, append-only, because current models bind thinking blocks to the conversation.

## D053 — Proactor runtime loop with synchronous trace writes (approved)
On Windows, MCP stdio clients spawn servers through anyio subprocesses, which need the default Proactor loop, while async Psycopg needs a selector loop (D013/D047). The runtime therefore runs on the default loop and writes runs/trace_events with synchronous Psycopg in a worker thread, keeping D013's IPv4 hint. Running a separate selector loop in a thread for database I/O was rejected as more complex for an append-only, low-volume writer.

## D054 — Explicit server environment, role toolboxes and argument locks (approved)
The runtime builds each server's environment explicitly (PYTHONPATH, database, user agent, snapshot, corpus, retrieval mode, offline flags) and never forwards API keys, following M3's finding that stdio clients pass only a minimal environment. Each role sees only its allowed tools, and worker tool arguments are locked to their structured subtask so a filings worker cannot widen ticker/year/period/items filters; this enforces the M3 cross-year lesson in code. The planner receives a deterministic, tested compact view of the 50-63 KB discovery result while the raw result stays in the trace.

## D055 — Decimal-string answers and structured subtasks (amends SPEC §10.4; approved)
Claim values and final values are fixed-point decimal strings compared by Decimal equality, matching D040's exact SEC values instead of SPEC's floats. Subtasks carry discriminated, typed parameters (ticker, metric, explicit periods; one filtered filing per search; computation inputs), and filing searches must specify fiscal year and period, so no worker reinterprets free text and no unfiltered search can be planned. Plans record every resolved time phrase and its discovery basis.

## D056 — Evidence ledger and deterministic checks before the LLM verifier (approved)
Every tool result is parsed into a run ledger; workers return IDs, and the orchestrator materializes exact values and verified quotes from the ledger rather than trusting model transcription. Deterministic checks (IDs produced in this run, exact numeric equality with the cited fact or computation field, computation-input lineage, unit/period consistency, status, final value and summary numbers) run before the LLM verifier, which then checks only textual support. With verifier=false the deterministic results are still recorded but change nothing, keeping the M6 ablation clean.

## D057 — Direct metric lookups instead of an LLM data worker (approved)
Because metric_lookup parameters are fully structured, the default executes get_financial_metric directly from the orchestrator; an LLM data worker could only copy those parameters while adding cost and a transcription failure mode. SPEC §10.5's small-model data worker remains available as `data_worker=llm` with locked arguments, for fidelity checks or an M6 ablation. The student approved `direct` as the default; the LLM data worker stays behind the flag and is tested offline.

## D058 — Model slots and environment variables (approved)
The analyst uses the large-model slot `PLANNER_MODEL`, workers `WORKER_MODEL`, and the verifier `VERIFIER_MODEL`; no ANALYST_MODEL variable is added. Experiment configs name environment variables rather than model IDs, preserving the rule that model IDs come only from the environment, and the resolved IDs are recorded in runs.config. For the OpenAI-compatible provider, unset role models default to `OPEN_MODEL`.

## D059 — Replayable traces and migration 004 (approved)
Traces store full provider responses, exact tool results, request fingerprints and incremental messages, keyed by deterministic agent-instance and tool-call identifiers so concurrent scheduling cannot change replay. Replay reruns the orchestrator with recorded responses and no SDK clients, servers or network, compares every request fingerprint and tool call, and requires an identical Answer hash. Additive migration 004 adds run finish/error/cache-token columns, a status check and `(run_id, seq)` uniqueness to the empty runs/trace_events tables; the approval is limited to those two tables.

## D060 — TOML pricing and run budgets (approved)
Prices live in a committed `filinglens/llm/pricing.toml` read by stdlib tomllib, because YAML support is deferred and TOML needs no dependency; this replaces SPEC §15's pricing.yaml name. Prices are decimal strings per million tokens for input, output and cache read/write; a model missing from the file fails preflight, and the prices used are snapshotted into runs.config. A shared per-run budget enforces MAX_RUN_TOKENS (all token kinds) and an optional max_cost_usd, and step limits raise BudgetExceeded.

## D061 — Mid-sentence passages handled without a server change (approved)
M3 showed a relevant chunk can begin mid-sentence (D050). In M4 the filings worker may run one extra search with the same locked filters using the passage's opening words to find the neighbouring chunk, and otherwise reports the gap; whole-section resources are not given to models because sections reach 100-200 KB. Adjacent-chunk IDs from get_passage remain an M6 candidate requiring approval to change the M3 server.

## D062 — Search-based treatment of the stretch diff question (approved)
The risk-factor diff is planned as one filtered Item 1A search per 10-K with the same query, and the analyst reports only differences it can cite, with a non-exhaustiveness caveat; a partial answer is expected. A deterministic runtime-side heading diff over both section resources was considered and is deferred unless the student approves it, since heading extraction from plain text is heuristic; it is an M6 candidate. If the diff run exceeds MAX_RUN_TOKENS, BudgetExceeded stops it, its trace and error are kept and reported, and the budget is not raised.

## D063 — JSON final outputs validated by Pydantic with one retry (approved)
Roles end with a JSON object validated by Pydantic and a semantic validator, with one corrective retry, as SPEC §10.3 describes; this works identically for both providers. Anthropic structured outputs and a forced "submit" tool were rejected for M4: forced tool choice is unavailable on current models, structured outputs are provider-specific, and parse failures should remain measurable. Strict tool schemas are not used because the server schemas use pattern and length constraints that strict mode does not support.

## D064 — Sampling, caching and refusal fallbacks off in M4 (approved)
The Anthropic provider sends no temperature/top_p/top_k (rejected under API version 2026-10-21); reproducibility comes from replay, not sampling. Prompt caching and server-side refusal fallbacks are off by default: caching changes cost accounting and fallbacks can silently change the serving model and price. Structured-output mode and strict tools also stay off (D063). Refusals surface as explicit run errors. Prompt caching is a cost decision to revisit at the start of M5, because M5 repeats the same prompts and tool specs across hundreds of runs; refusal fallbacks remain an M6 option.

## D065 — Phase B implementation details (approved)
Periods the server returns without a fact (unavailable/not_applicable) get deterministic citable IDs `na_<ticker>_<metric>_<year>_<period>`; they carry no value, so D056 forbids numeric claims on them. Per-call `max_tokens` is fixed at 16,000 instead of Phase A's min(role maximum, remaining budget), because the remaining budget depends on concurrent scheduling and would make replay fingerprints nondeterministic. The token budget is checked before every call, so a run can exceed MAX_RUN_TOKENS by at most one LLM call before BudgetExceeded when agents run sequentially; while workers run concurrently, each in-flight agent can complete at most one such call (at most four under the default concurrency cap). Worker quotes are verified by whitespace-normalized exact substring match; an MCP request timeout becomes a `TOOL_TIMEOUT` tool result while other protocol or transport failures fail the run; a filings worker whose output stays invalid is recorded as "not found" rather than failing the run.

## D066 — Module CLI now, console script deferred to M7 (approved deviation)
The uv project is virtual (no build backend), so `[project.scripts]` would not install a `filinglens` command. M4 runs the CLI as `python -m filinglens.cli ask|replay`, a deviation from SPEC §10's `filinglens ask`; the console script is deferred to M7 packaging, and no build backend is added now. Ruff excludes docs/ so formatting never rewrites approved design records such as M4_PHASE_A.md.

## D067 — Duplicate tool calls answered from the agent instance's earlier result (approved)
At M4 acceptance two agents looped on identical calls until max_steps. Within one agent instance, a model-issued call identical to an earlier successful call (same server, tool and canonical JSON arguments) is not executed again: it gets the earlier result prefixed with "duplicate call: result already provided (call <id>)", keeps the earlier computation ID (no new cmp_N), and is still traced as tool_call and tool_result with duplicate_of. Error results are not memoized, so a failed call (for example a timeout) may be retried; orchestrator-issued prefetches never enter the memo, so the model is not told it saw a result it did not. Because the memo depends only on call order and arguments, replay reproduces the same duplicates without re-executing them (tested offline). Runs recorded before D067 that contain duplicates no longer replay identically under the new code; their recorded replay results stand.

## D068 — Final-step guard with tool_choice none (approved)
On an agent's last allowed step (step max_steps-1, only when it has tools), the loop appends a user message: "This is your last step: tool calls are disabled. Do not call any tool. Reply now with only the final JSON object, using the results you already have." and sends tool_choice none. Anthropic's current docs list tool_choice {"type": "none"} ("Claude cannot use tools") as unaffected by the forced-tool-choice removal on Claude Sonnet 5.5/Opus 5.5/Fable 5.1, and SDK 2.1.0 types it (ToolChoiceNoneParam). The request keeps the identical tools list instead of omitting it: Anthropic's own tooling sets tool_choice none on requests with tool history but never removes tools, because the tool set is part of the prefix that prompt caching and preserved thinking compare. So a tool call on the final step is impossible on the API, not just discouraged; the OpenAI-compatible provider sends tool_choice "none". LLMRequest.tool_choice is excluded from the request fingerprint when unset, so pre-D068 traces keep their fingerprints.

## D069 — Period resolutions must name their companies (approved)
When a plan lists companies, every period_resolutions entry must set ticker to one of them; a null ticker is rejected with feedback (via the existing single corrective retry). A phrase that genuinely applies to every company uses the new optional tickers field, which must list exactly all plan companies; setting both ticker and tickers is rejected. Plans with no companies (not_available/out_of_scope) are unchecked. The planner prompt gains one sentence describing ticker/tickers. This changes the Plan JSON schema appended to the planner prompt.

## D070 — Verifier Stage 2 reviews caveats (approved)
Caveats were outside both verification stages (the M4 Microsoft run carried an unchecked "latest filing in the snapshot" statement). Caveats are now identified positionally as caveat_1..caveat_N; each unverified caveat text is sent to the LLM verifier with the run evidence (the analyst's evidence pack plus every successful computation, since caveats carry no citations), and VerifierOutput gains caveat_verdicts with exactly one verdict per caveat id. A caveat that is not supported is a failure like a claim: the analyst gets it in revision feedback ("caveat_N is the N-th entry of caveats"), and if it is still flagged after the last revision round it is removed and replaced by "Removed unsupported caveat: <reason>". Supported caveat texts are not re-sent in later rounds. There is no deterministic Stage 1 check for caveats. The verifier prompt gains one bullet; the analyst-facing revision instruction (runtime text, not a prompt file) names caveats.

## D071 — First filing-search latency observed at M4 acceptance (diagnosis only; no change)
The Tesla run's first search_filings took 51.2 s versus 8.5/8.0 s in the Meta run. Trace and server-log timestamps show all of it was spent before SentenceTransformer construction (call 10:58:01.4, "Loading SentenceTransformer model" 10:58:52, result 0.6 s later), that is, in the lazy first import of transformers, torch and sentence_transformers inside the freshly spawned edgar-mcp process. Measured warm, those imports take 6-8 s and tokenizer, model load and first encode under 0.5 s. The Tesla search was the first import of that stack from the .venv rebuilt at 04:13 with copy mode (0.89 GB of new files, torch_cpu.dll 292 MB; no retrieval-cache entry was written between the rebuild and 10:58, and the test suite's searches hit the frozen retrieval cache), so the files were read cold, very likely with Windows Defender real-time scanning on first load (real-time protection is on; scan logs need administrator access, so this part is inferred). Structural consequence: every run spawns new servers and pays about 7 s on its first search; a first run after a venv rebuild or reboot can pay about 50 s. Preloading the embedder at server start or reusing long-lived servers would remove this but changes M3 servers or the runtime's lifecycle; deferred to M5/M6 for approval.

## D072 — Revision rounds reserve their own budget (approved)
At the post-fix acceptance run two answers were lost because the token budget ran out during a revision. Before starting a revision round the orchestrator now estimates its cost from this run's measured usage: (largest single analyst call + largest single verifier call, all token kinds) x 1.5, the margin covering the longer revision prompt. RunBudget records the largest call per role in add(), from the same recorded usage in live runs and in replay, so the decision replays deterministically. If the estimate exceeds the remaining MAX_RUN_TOKENS, the round is skipped and the answer is finalized with the normal end-of-revisions rule (_drop: failing claims and caveats move to caveats), and a revision_skipped trace event records the round, estimate, remaining tokens and dropped items. The estimate covers a one-call revision; a revision that uses tools or overruns is caught by D073.

## D073 — A budget stop after a draft finalizes instead of discarding the answer (approved)
If BudgetExceeded (tokens, cost or steps) is raised after the first analyst draft exists, the latest complete draft is finalized without further LLM calls. Stage 1 checks are rerun on it (no tokens); a claim is kept only if it passes Stage 1 now and its exact current form already received a Stage 2 "supported" verdict in this run. The summary is kept only on the same terms (otherwise it is rebuilt from kept claims), and only Stage 2-verified caveats are kept. Everything else moves to caveats as "Removed unverified claim/caveat: <text> (reason)", a caveat states that verification was cut short and by which limit, and the status becomes partially_answered, or not_available when no claim remains. The run row keeps status done and records the stop in runs.error as {"type": "BudgetExceeded", "kind", "message", "handled": "budget_finalized"} (no schema change), and a budget_finalized trace event lists kept and dropped items; the CLI prints it as "budget finalized". A stop before any draft exists is still a run error. Replay reproduces finalization because the replay gateway applies the same pre-call budget check to the recorded usage. With this change _drop also includes the dropped caveat's text, as it already did for claims.

## D074 — Filings workers may read at most four full passages (approved)
Run-to-run variation in how many passages a filings worker reads was the main token driver of the post-fix budget overruns. Each filings worker's toolbox now caps executed get_passage calls at RunConfig.max_passage_reads = 4. The count is assigned in call order before concurrent execution, so it is deterministic; rejected calls, duplicates (D067) and orchestrator prefetches of cited passages do not count. A call over the cap gets a CALL_LIMIT tool result telling the worker to use the passages and snippets it has and return its final JSON. Search limits are unchanged, and the filings worker prompt is unchanged.

## D075 — Derived facts carry their derivation into the evidence (approved)
The verifier could not check the analyst prompt's derived-Q4 caveat because evidence showed only derived: true. Fact records for derived values now include a derivation block built from the server's derivation_inputs: a formula with signed values and periods, whether the inputs reproduce the stored value, and each input's value, coefficient, concept, period, source accession and fact_id. It reaches the analyst (evidence pack) and the verifier (cited sources and run evidence) automatically. Edgar-mcp's derivation inputs carry no fact IDs, and a year-to-date input is not a stored fact at all, so fact_id is filled only when the input matches a fact already fetched in this run (same period and value) and is otherwise null with a note; exposing input fact IDs would need an M3 server change and is not proposed. The analyst prompt's derived-Q4 caveat wording is unchanged.

## D076 — Hedged caveat speculation is unsupported (approved)
After the Costco membership-fee caveat passed Stage 2 as a hedged limitation, the verifier prompt's caveats bullet gains one sentence: hedged speculation ("may", "might", "could") about values or definitions that the evidence does not support is unsupported, the same as an unhedged statement.

## D077 — The verifier always sees the whole current answer (approved)
Post-fix run 2 showed the verifier rejecting correct summaries in 4 of 6 runs because run_verifier sent only the claims still awaiting a verdict (Phase B behavior), often none. Every verifier round now receives every current claim, every caveat keyed caveat_1..caveat_N, and the cited sources for every claim; the task text lists the claim and caveat ids that need verdicts (those without a current supported verdict), names the already-verified claims as context only, and always asks for the summary verdict, so the summary and final value are judged against the full current claim set. The output contract is unchanged: exactly one verdict per requested claim id and caveat id, so a verdict on an already-verified claim is rejected through the normal retry. The instruction is runtime task text; verifier.md is unchanged. Verifier input grows with the answer size.

## D078 — No internal verifier text in user-facing caveats (approved)
Removed items no longer put claim text or verifier reasons into Answer.caveats. _drop adds at most one neutral line per kind ("1 claim could not be verified and was removed." / "N claims ...", the same for caveats) and, when the summary is replaced, "Summary rewritten from verified claims."; budget finalization (D073) keeps its single "Verification was cut short by ..." caveat. The full text and reasons of every removed item are recorded in the trace: the end-of-revisions verification event, revision_skipped (D072) and budget_finalized (D073) events carry a removed map (id -> text, reasons), and the verification events keep every verdict and reason. In the analyst prompt, the instruction to caveat "values reflecting the latest filing within the snapshot" is removed (citations already name the filing; Stage 2 rejected that caveat in three runs).

## D079 — Quant calls must consume a value from the evidence (approved)
Analyst stalls issued calculations with no evidence values (margin(1, 1), evaluate("1"), evaluate("0")). The analyst's toolbox now rejects a quant call when none of its numeric inputs, including literals inside an evaluate expression, equals (in absolute value) a fact value or a number in an earlier successful computation output in this run's ledger. The tool error is UNTRACED_INPUTS: "This calculation uses no values from the evidence. If your calculations are complete, return the Answer now." Small integer constants remain allowed alongside at least one traced value (the D056 lineage rule still checks every input of cited computations). The check runs before execution in call order, rejected calls are never registered in the ledger, and errors are not memoized (D067), so behavior is deterministic and replays identically.

## D080 — Analyst stall diagnosis (observation; no change)
In the recorded stall steps (Nvidia, Walmart/Costco; also pre-fix Nvidia) the model returned only tool_use blocks: no text, 49-71 output tokens per call, and in two steps a thinking block whose text is empty because Sonnet 5.5's default thinking display returns no thinking text. The stall calls contain no evidence value, and as soon as the final-step guard sent tool_choice none the model wrote a complete, correct Answer of 1,273-3,073 tokens, so it already had what it needed. The recorded data therefore cannot show the model's reason; the observable pattern is that it issues a trivial tool call instead of ending its turn before a long final JSON. Seeing the reasoning would need thinking.display "summarized" (or "updates"), a request change that affects only visibility and is an M5/M6 diagnostic option for approval.

## D081 — Wider timing tolerance in the SEC pacing test (test-only)
tests/test_client.py::test_concurrent_request_pacing asserted every gap between paced requests was at least 0.115 s (8 requests/s, 0.125 s interval) and failed once in a full-suite run during M4 acceptance while passing alone. Windows timers tick about every 15.6 ms, so a single asyncio.sleep can end early under load. The test now derives the interval from settings and allows each gap to be 20% short, while requiring the total span of the three gaps to be at least 90% of three intervals, so a client that does not pace still fails. The SEC client's pacing logic is unchanged.

- M6 candidate: thinking.display "summarized" (or "updates") for the analyst, to see the reasoning behind tool-call stalls (D080); it affects visibility only.

## D083 — Generated benchmark v1 (approved)
Seven SPEC §13.1 templates (lookup, yoy_growth, margin, trend_avg, derived_q4, comparison, multi_step) with fixed wording, generated only from financial_facts of snapshot 2026-10-19-v1 with Decimal arithmetic (precision 80, ROUND_HALF_EVEN, as quant-mcp); no LLM ever produces a gold value. Target 400 questions (60/60/60/55/55/55/55), balanced across companies and metrics by a seeded greedy pass; periods without a fact (unavailable/not_applicable, banks' gross profit), non-positive growth bases, EPS outside lookup/yoy_growth and instants outside lookup are skipped. Each record carries the gold, unit, tolerance, companies, periods, gold_fact_ids, the computation and its inputs, SEC URLs and fairness metadata. A separate ~10-question abstention probe (banks' gross profit and margins, banks' operating income) has status-only gold and is reported outside the headline.

## D084 — Dev/test discipline, the frozen set and the B1/B2 sample (approved)
The split is 30% dev / 70% test, stratified by template, ordered by SHA-256(seed, id) with seed 20261109. All prompt and design tuning uses dev only; final numbers are reported on test only. Once the student approves the review sample, the question file and its manifest (SHA-256, counts, seed, generator version, snapshot) are frozen and hash-checked by tests and the runner, and are never regenerated in place (a change is a new version). One 100-question test sample, stratified by template with the same seed, is chosen at generation and frozen with the set; B1 and B2 run only on it, and their comparisons include the system's and B0's results on the same 100 questions.

## D085 — Tolerances, units and abstentions (approved)
Currency and averages: relative error ≤ 0.5%; percentages and percentage points: absolute ≤ 0.1; diluted EPS: ≤ max(0.5% relative, $0.005), so cent-rounded small EPS values are not penalized; comparison also requires the correct company. Predictions are normalized from raw/thousands/millions/billions, per-share, percent/fraction and pp; a value that would match only under a different scale is incorrect and counted as a unit-rescue diagnostic, never silently accepted. not_available/not_applicable answers to questions with a gold value are incorrect and reported as abstentions, separately from wrong values and parse failures.

## D086 — Fairness metadata (approved)
Every question records period_end_max and first_filed_max, the latest original filing date among all gold inputs (from the frozen companyfacts JSON). The cutoff bucket per model is before (first filed ≤ 2026-05-31), june, or after (≥ 2026-07-01), using the official "Jun 2026" training/knowledge cutoffs of Sonnet 5.5 and Opus 5.5. restated is true when the gold recomputed from each input's earliest-filed observation differs from the latest-filed gold; derived_q4 marks any derived input. At least 20% of each template comes from after-cutoff periods where the pool allows (the natural share is about 7%); results are reported both overall and noting the floor.

## D087 — Baseline protocol (approved)
B0, B1 and B2 share one system prompt and a final one-line JSON answer {value, unit, choice, status}; parsing and scoring are identical for baselines and the system (last JSON object with a value key; missing/unparseable is a parse failure). Baselines use each model's default thinking and effort, like the system, no sampling parameters and max_tokens 16,000. B0 runs on claude-sonnet-5-5 and claude-opus-5-5 in real time on the full test split; no Fable model for now (a possible later B0 add-on on the sample if budget remains).

## D088 — B1 web search (approved)
B1 is Sonnet 5.5 with the server-side web_search_20260209 tool, max_uses 5, open web, on the frozen 100-question sample, run through the Batch API (50% off); its latency is reported as "batch, not comparable". Searches cost $10 per 1,000 plus result tokens, added to cost_usd; pause_turn continuations are allowed up to 3.

## D089 — B2 stuffed financial statements (approved, amended cap)
B2 is Sonnet 5.5 on the frozen 100-question sample via the Batch API. Its context is the financial statements window (income statement through cash flows, up to the notes) of each filing that holds a gold input, taken from the frozen raw snapshot because corpus v2 has no 10-Q statements, capped at 25K tokens per filing and 50K per question; older filings are truncated first and context_truncated is recorded. gold_visible records whether every gold input value appears in the stuffed text at the filing's printed scale, and B2 results are reported overall and for gold-visible questions.

## D090 — Runner, cache and spend caps (approved)
Runner configs are TOML (stdlib tomllib; YAML remains deferred). Each answer is cached atomically on disk under (system config hash, question id), with the question-text hash checked; the cache is the resume checkpoint and lets reruns and CI replays cost nothing. The system config hash covers system kind, resolved model IDs, prompt and tool-spec hashes, flags, baseline settings, snapshot/corpus IDs and runner version, but not prices. Every invocation enforces a hard spend cap, reserving each in-flight question's maximum cost; when spent plus reserved reaches the cap it schedules nothing new, lets in-flight work finish, marks the rest skipped_spend_cap and remains resumable. Caps: dev pilot $20, test run $70, total ceiling $90 (student limit $100). A replay-only mode serves only cached records, builds no SDK client and needs no keys or database.

## D091 — System adapter and the comparison choice (approved compromise)
The system's prediction is its Answer's final_value, final_unit and status. The M4 Answer has no "choice" field and changing it would change runtime behavior, so for comparison questions the choice is the ticker of the higher of the system's two percent claims that carry tickers; if that cannot be resolved it is a parse failure. Baselines report choice in their JSON.

## D092 — Citation validity (approved)
System only. Numeric claims: M4's Stage 1 check_claim is rerun offline on the final Answer against the ledger rebuilt from the run's recorded tool results. Text claims: supported by string match first (a verified quote of the cited chunk with matching key numbers or phrases), otherwise an Opus 5.5 yes/no support judge.

## D093 — LLM judge and calibration (approved)
For the 30 handwritten explanatory questions, Opus 5.5 scores answers 1-5 against the student's reference answer (rubric in M5_PHASE_A §5), seeing content but not citations, and returns JSON. The student labels 20 judge outputs blind, stratified across scores and systems; exact agreement, within-1 agreement and quadratic-weighted Cohen's kappa are reported, and the judge is reported as indicative only if kappa < 0.6. System-level retrieval recall@5/10 comes from the trace; the frozen M2 v2 retrieval table is reused verbatim.

## D094 — Statistics (approved)
Accuracy CIs are percentile bootstraps (10,000 resamples, fixed seed). System vs each baseline uses an exact McNemar test on identical questions with Holm correction across baselines, plus the paired accuracy difference with a bootstrap CI; B1/B2 comparisons use the frozen 100-question sample. Results are broken down by template, cutoff bucket, restated, derived and (B2) gold_visible; subgroups with n < 30 are labeled descriptive.

## D095 — D082 resolutions for M5 (approved)
Prompt caching stays off: M5 measures the accepted M4 system, and caching would be a runtime change; it is an M6 cost experiment. Budget reservation under concurrency is unchanged (overshoot is bounded by D065; the runner reports any run over MAX_RUN_TOKENS). MAX_RUN_TOKENS stays 200000; numeric templates used 27K-130K tokens in M4 and D072/D073 handle overruns. The run budget is not cost-weighted: max_cost_usd already caps dollars per run and the runner caps the invocation.

## D096 — Model cutoffs and versions (approved)
Training-data and reliable-knowledge cutoffs come from the official models overview (checked 2026-11-09): Jun 2026 for Sonnet 5.5, Opus 5.5, Haiku 5.5 and Fable 5.2. Claude Fable 5.2 has superseded Fable 5.1; neither is used in M5 for now. A later model gets its own cutoff bucket from its documentation.

## D097 — Mixed-vintage derived quarters excluded (approved 2026-11-11)
13 of the 563 stored derived facts subtract inputs from different filings where at least one input was later restated (e.g. BAC FY2024 revenue as restated in the 2026 10-K, 105,856M, minus the original 9M total from 2024 10-Qs; first reported FY was 101,887M). Such a "quarter" was never reported by anyone, so its gold is not checkable against any single filing. `evals/generate.py` drops these facts before generating candidates (`EXCLUDE_MIXED_VINTAGE = True`); M1 rows are unchanged (D009 stands). Restated *direct* facts stay in the set and are flagged `restated` with the gold recomputed on first-reported values.

## D098 — Cache key carries the resolved model ID; split is not part of it
A baseline's cache key includes the model ID resolved for its `model_env[model_index]`; the runner refuses to hash a blank ID. Before this fix B0 Sonnet and B0 Opus (BASELINE_MODELS index 0 and 1) would have shared cache entries. The split is not part of any key: question IDs are unique across splits, so the full test run's system and B0 records also serve the 100-question B1/B2 comparison table (D088) without re-running them.

## D099 — System retrieval recall with several workers
System-level recall@k unions each filings worker's first-search top k. The D027 denominator min(k, |gold|) is per search, so with w workers the denominator is min(k x w, |gold|); recall can no longer exceed 1 on comparison questions.

## D100 — B2 statements heading detection
The statements window starts at a heading that matches the statement pattern with whitespace removed (Microsoft's markup splits "INC OME STATEMENTS"), is not a contents row, and is followed within 11 blocks by 4 numeric rows with no prose paragraph (> 200 chars) before them (rejects policy notes titled "Income Statement - ..."). On the draft sample: 0 fallbacks, gold visible 97/100 (DIS operating income is not printed on its income statement; a BAC cash-flow value and one MSFT input fall past the 25K/50K caps), 3 contexts truncated.

## D102 — Baseline model IDs from RuntimeSettings; runner preflight
`BASELINE_MODELS` is a `RuntimeSettings.baseline_models` field (comma-separated, blank is unset), read by pydantic-settings from the environment or `.env` like the other model IDs; the runner no longer imports python-dotenv, so Settings is the only `.env` reader. ## D103 — Eval runner: one MCP hub per invocation, clean shutdown, replay keys
The M5 dev pilot (2026-11-11) answered all 200 questions but never exited: each of the 4 concurrent workers found no hub and opened its own (4 edgar + 4 quant servers), and the hubs were entered inside worker tasks and never closed, so `asyncio.run` hung in teardown before `main` wrote the run summary. The process was stopped manually and the summary rebuilt from the cache (`evals/results/runs/m5-dev-pilot-reconstructed.json`). Fixes, eval harness only (the M4 runtime is unchanged): `system_runner` returns a lifespan that opens one hub per retrieval mode in use (normally one) and workers fail fast if no hub is open; `Runner.run` enters that lifespan in its own task before any worker starts and exits it in the same task (anyio cancel scopes must be exited where entered) on every path, cancelling sibling workers first when one aborts; the run summary always gets a status (completed, error, interrupted), finish time and spend, and `main` writes it in a `finally`. A third defect found while rebuilding: `--replay-only` and `report.py` used an empty `Deps`, so the system's and baselines' cache keys (resolved model IDs, prompt hashes) never matched the live run; `replay_deps` now computes exactly those keyed settings from Settings and the prompt files, still with no SDK client, MCP server or database. `RUNNER_VERSION` is unchanged because no answer changes, so the dev-pilot cache stays valid; a fully cached rerun of the live command exited in 7 s with no MCP processes left.
